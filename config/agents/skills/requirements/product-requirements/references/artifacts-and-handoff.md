# 产物与工具契约

下列契约对应本模块现有工具。以当前会话实际工具定义和返回值为准；Skill 不提供额外工具，也不允许绕过导入确认、记录归属或版本校验。

## 保存规格与候选待办

`requirements_save_draft` 的参数只有 `id?`、`title`、`note?`、`priority?` 和 `taskDrafts`。

- title 为 1–200 字，note 最多 5000 字；priority 为 low / normal / high，未指定可沿用工具默认 normal，不冒充用户决定。
- taskDrafts 为 1–20 项，每项只含 title、priority?、due?、tag?；due 是 YYYY-MM-DD 或 null，表示截止日期，不表示已经安排到某天。
- 业务规则、权限、依赖、详细验收写在 note，不向工具添加 userStory、acceptanceCriteria、description、dependencies 等未知字段。
- 没有实际候选工作时先在会话中整理探索成果，不能虚构“补充需求”等占位待办来满足 minItems。
- 新草稿省略 id；修订同一草稿使用真实返回 id。只能修改本会话未导入草稿，sourceSessionId 由服务端注入。
- 已导入草稿不可由该工具重写；遇到变更先核对关联需求与当前版本，说明已有任务和验收受影响的部分，不另建相同草稿规避限制。现有工具不能表达的变更请用户在需求记录中审阅处理，不声称已经更新业务记录。

普通页面保存只产生草稿，用户通过界面预览、调整、确认后导入。不要自行用 bash 或 HTTP 绕过该确认点。保存成功以返回记录为准；失败不宣称保存成功；写入结果未知先核对，不盲目重复新建。

## 从规格拆为候选工作

按用户可获得的能力或可独立验收的成果拆分，避免默认按前端/后端/数据库机械切碎，也不要遗漏确实需要的验证工作。每项应说明它对应哪条需求及哪些验收条件；详细映射写在 note，标题可简短引用局部编号。

例如在已明确的选择导入需求中：

- note 中写 FR-01（只导入用户选择项）、FR-02（确认前不创建）、FR-03（同一次重试不重复）；分别给出 AC-01/02/03 的可观察结果。
- 待办标题可为“实现选择导入与确认流程（FR-01/02；AC-01/02）”和“实现重试防重复并验证（FR-03；AC-03）”。

这些编号不是服务端任务 ID。只有工具返回后才引用真实 requirementId、taskId。日期、负责人或技术方案没有依据时不代填；依赖、建议与未决项留在 note。超过 20 项先按可验收成果归并；无法合理归并时说明限制，与用户确定分批范围，不静默截断或自动建多个需求。

## 群聊实施交接

只有群里被点名接到需求实施任务，且本次实施的关键决定已明确，才使用 `requirements_dispatch`。仅探索、评审或保存不代表实施授权。限定清楚的独立子范围可按已有授权推进，其他部分保留待决。

dispatch 参数为必需的 entryKey、title、note、taskDrafts，以及可选 id、priority；note 必须写出范围、规则、约束和对应验收。entryKey 为 1–80 个字母、数字、下划线、点、冒号或连字符；同一次调用重试保持 key 与内容不变。工具原子保存并导入，返回真实 requirement 与 tasks，不能用 save_draft 代替后宣称已导入。

- 复用当前交接关联的未导入草稿时显式传 id；同话题中的新需求省略 id，不覆盖原需求。
- 成功后调用 `chatroom_send`，正文以“@代码开发 ”开头，交代目标、范围与非目标、规则/约束、真实待办及验收、必要证据和剩余非阻塞假设。引用由服务端传递，不要求助理重复建待办。
- 普通页面已有草稿且用户明确要求群里实施时，`chatroom_send` 发“@需求管理 ”，同时传真实 requirementId、返回记录的 updatedAt（expectedUpdatedAt）与 requirementVersion。接收会话复用草稿，不从普通页面直接调用 dispatch。
- 遇到版本冲突先重新核对实际记录，不能猜最新修订号或换新 key 掩盖重复/冲突。

发出交接只说明已经投递。依赖开发回报时用 `chatroom_work` 更新 waiting_for_agent 并结束当前回合，不轮询同事。关键决定需用户补充为 waiting_for_user；分工 completed、业务待办完成和用户接受是不同状态，遵守系统提示词的持续工作纪律。

## 回报、变更与验收

使用 `chatroom_trace` 核对当前关联需求版本、待办、协作分工、Run、工具结果和交付；普通需求会话只能读自己保存的需求。收到完成回报时对照本版验收与真实证据，不重新 dispatch。需求 Agent 不代替我的助理更新业务待办完成状态。

`chatroom_delivery` 只在关联需求的群工作会话中提交当前版本的真实证据，不能接受交付。证据 kind 只取 file / commit / pull_request / test / report，ref 和可选 toolCallId 必须可核验；未跑测试写“未验证”，不能用猜测的文件或成功结果充数。

功能验收要看当版行为和证据；业务成功要看定义好的指标与观察周期。自己的分工完成、证据已提交、用户正式接受分别汇报。用户改动范围或规则后，重新核对受影响的验收和任务，旧版证据不能自动算新版通过。
