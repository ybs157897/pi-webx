# 产物与工具契约

下列契约对应本模块现有工具。以当前会话实际工具定义和返回值为准；Skill 不提供额外工具，也不允许绕过导入确认、记录归属或版本校验。

## 资料读取与目标定位

当前会话绑定的工作空间整体就是当前项目；根目录包含多个模块也不改变项目身份，不要再询问项目名称。服务端需求上下文提供绑定身份与已有需求摘要；摘要不表示用户选中其中某条需求。requirements_context 只读公开需求记录，可按 requirementId 核对正文与版本，或按 query、limit 查询有限摘要，查询结果不是实施授权。本会话若提供 read、ls、grep、find，可在绑定工作区内只读检索 README、源码、项目配置与直接相关材料；不能读取父目录、用户全局文件、其他 Agent 私有会话或其数据库、用户全局或运行器私有配置。read/write/edit/ls/grep/find 均只在本工作区内使用，符号链接不能扩大范围；write/edit 只用于用户要求的需求文档。requirements/ 是需求库自动生成的只读投影，可能滞后；核对需求以 requirements_context 返回的当前记录为准，不把投影文档当成可编辑事实，也不通过文件工具改写它。不通过 shell 或 HTTP 绕过读取范围。

## 保存规格与候选待办

`requirements_save_draft` 的业务字段为 `id?`、`title`、`note?`、`priority?`、`category?` 和 `taskDrafts`，另有请求级幂等键 `entryKey?`。`entryKey` 不会写入需求记录。

- title 为 1–200 字，note 最多 5000 字；priority 为 low / normal / high，未指定可沿用工具默认 normal，不冒充用户决定。
- category 取 `new | change | fix | enhancement`（默认 new）：new=新功能、change=需求变更、fix=问题修复、enhancement=体验优化；按变更判定结果选择，change 应在 `## 变更判定` 写明对应历史需求的 REQ-ID。
- taskDrafts 为 1–20 项，默认恰好 1 条（见「成文与单条待办」），每项只含 title、priority?、due?、tag?；due 是 YYYY-MM-DD 或 null，表示截止日期，不表示已经安排到某天。
- 业务规则、权限、依赖、详细验收写在 note，不向工具添加 userStory、acceptanceCriteria、description、dependencies 等未知字段。
- 没有实际候选工作时先在会话中整理探索成果，不能虚构“补充需求”等占位待办来满足 minItems。
- 新需求省略 id；只有修订本会话的未导入草稿才传其真实返回 id，服务端拒绝改写已导入或非本会话的记录。sourceSessionId 由服务端注入。
- 同一逻辑保存重试时保持 entryKey 和业务参数不变；省略 entryKey 时只用 SDK 的 toolCallId 识别同一调用重放。相同 entryKey 配不同参数会冲突；不同需求必须使用新 entryKey，即使标题或内容相似也不会自动合并。
- 返回 `alreadySaved:true` 表示复用了原保存回执；其中记录和 requirementVersion 是首次保存的快照，可能早于后续修订或导入。交接前用 `requirements_context` 核对当前记录与版本，不把回执快照当成最新状态。
- 已导入或非本会话的需求记录不可由保存工具改写：不传其 id 保存、不新建相同草稿规避限制，也不把变更判定当成已经修订原需求。对这类记录的变更按「变更判定与版本时间线」新建 change 记录，由用户在需求记录中审阅合并，不声称已经更新业务记录。

普通页面保存只产生草稿，用户通过界面预览、调整、确认后导入。不要自行用 bash 或 HTTP 绕过该确认点。保存成功以返回记录为准；失败不宣称保存成功；写入结果未知先核对，不盲目重复新建。

## 成文与单条待办

note 按固定章节成文：`## 目标`、`## 详细内容`、`## 范围影响`（受影响功能点与对策，逐点写明定位依据与处理方式）、`## 验收标准`；category 为 change 时补 `## 变更判定`（对应哪条历史需求、为何算变更、受影响的旧验收）。章节内按影响裁剪，不机械填满模板。可给功能与验收设 FR-01、AC-01 等局部编号，这些是文档编号，不是服务端任务 ID。

taskDrafts 默认恰好 1 条，标题表达这个需求的整体交付，可引用需求标题；FR/AC 与阶段步骤等实施拆解写在 note，不外溢成多条待办。只有用户明确要求分批排期时才拆多条：那时按可独立验收的成果拆分，避免按前端/后端/数据库机械切碎，也不要遗漏确实需要的验证工作；每项说明它对应哪条需求及哪些验收条件，详细映射写在 note。

例如在已明确的选择导入需求中：note 写 FR-01（只导入用户选择项）、FR-02（确认前不创建）、FR-03（同一次重试不重复），并分别给出 AC-01/02/03 的可观察结果；默认待办标题为“实现选择导入与确认流程（FR-01/02/03；AC-01/02/03）”。用户明确要求分批排期时，才按可独立验收的成果拆成多条并说明对应编号。

只有工具返回后才引用真实 requirementId、taskId。日期、负责人或技术方案没有依据时不代填；依赖、建议与未决项留在 note。确有分批需要但超过 20 项时先按可验收成果归并；无法合理归并时说明限制，与用户确定分批范围，不静默截断或自动建多个需求。

## 变更判定与版本时间线

成文或派工前先用 requirements_context 按主题（功能名、行为关键词）检索历史需求，再按 requirementId 读取候选记录与当前版本，判断本次是否落在已有功能上：

- 对应功能已有记录：判定为 change。该记录是本会话的未导入草稿时，传其真实 id 修订；已导入或非本会话时不改写原记录，新建 change 记录。note 补 `## 变更判定`，写明对应哪条历史需求（REQ-ID）、为何算变更、受影响的旧验收，并说明已有任务中哪些需要重审或回归；是否并入原需求由用户在需求记录页决定。
- 只是相似名称但属于另一个功能：不复用旧 id，按新建处理，避免把两条生命周期的历史混在一起。
- 只有确认问题修复才标 fix，体验优化标 enhancement；判不准时用 new 并在正文说明依据，不把不确定的修复当成已验证的问题。

版本冲突（expectedUpdatedAt 过期，或交接后记录已被修改）先重新用 requirements_context 核对当前记录与版本，不猜测或伪造新版本号，也不用新 entryKey 掩盖冲突。

## 群聊实施交接

只有群里被点名接到需求实施任务，且本次实施的关键决定已明确，才使用 `requirements_dispatch`。仅探索、评审或保存不代表实施授权。限定清楚的独立子范围可按已有授权推进，其他部分保留待决。

dispatch 参数为必需的 entryKey、title、note、taskDrafts，以及可选 id、priority、category；note 必须按固定章节写出目标、范围、规则、约束和对应验收，taskDrafts 默认只有 1 条。entryKey 为 1–80 个字母、数字、下划线、点、冒号或连字符；同一次调用重试保持 key 与内容不变。工具原子保存并导入，返回真实 requirement 与 tasks，不能用 save_draft 代替后宣称已导入。

- 传 id 复用仅限两类：本会话保存的未导入草稿，以及当前投递明确关联且 expectedUpdatedAt 仍匹配的未导入草稿（含普通页面转交到群的场景）；除此之外的历史记录一律新建，不覆盖原需求。
- 本次落在已有需求上时标 change 并在 `## 变更判定` 写明对应 REQ-ID；已导入或无关联的历史需求新建记录，不自行宣告版本或声称已修订原需求。
- 成功后调用 `chatroom_send`，正文以“@代码开发 ”开头，交代目标、范围与非目标、规则/约束、真实待办及验收、必要证据和剩余非阻塞假设。引用由服务端传递，不要求助理重复建待办。
- 普通页面已有草稿且用户明确要求群里实施时，`chatroom_send` 发“@需求管理 ”，同时传真实 requirementId、返回记录的 updatedAt（expectedUpdatedAt）与 requirementVersion。接收会话复用草稿，不从普通页面直接调用 dispatch。
- 遇到版本冲突先重新核对实际记录，不能猜最新修订号或换新 key 掩盖重复/冲突。

发出交接只说明已经投递。依赖开发回报时用 `chatroom_work` 更新 waiting_for_agent 并结束当前回合，不轮询同事。关键决定需用户补充为 waiting_for_user；分工 completed、业务待办完成和用户接受是不同状态，遵守系统提示词的持续工作纪律。

## 回报、变更与验收

使用 `chatroom_trace` 核对当前关联需求版本、待办、协作分工、Run、工具结果和交付；普通需求会话的生命周期追踪仍限于自己保存的需求。requirements_context 的只读公开记录查询不扩大追踪或修改权限。收到完成回报时对照本版验收与真实证据，不重新 dispatch。需求 Agent 不代替我的助理更新业务待办完成状态。

`chatroom_delivery` 只在关联需求的群工作会话中提交当前版本的真实证据，不能接受交付。证据 kind 只取 file / commit / pull_request / test / report，ref 和可选 toolCallId 必须可核验；未跑测试写“未验证”，不能用猜测的文件或成功结果充数。

功能验收要看当版行为和证据；业务成功要看定义好的指标与观察周期。自己的分工完成、证据已提交、用户正式接受分别汇报。用户改动范围或规则后，重新核对受影响的验收和任务，旧版证据不能自动算新版通过。
