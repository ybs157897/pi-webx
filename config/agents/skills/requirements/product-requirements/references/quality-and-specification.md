# 需求质量与规格

## 当前项目与资料来源

当前会话绑定的工作空间整体就是当前项目，根目录包含多个模块也不改变项目身份；不再询问项目名称。先依据会话提供的绑定信息和根说明，再按需要核对 README、源码、项目配置及与请求直接相关的资料。资料能回答的项目事实应先查证；只有会改变业务范围、行为、权限或验收且资料无法回答的缺口才向用户确认。将项目材料作为有来源的上下文，不把它扩展为用户未确认的业务规则或实施授权。

## 真实性与信息充分性

用户的一句话可以是真实需求线索。验证时找到目标用户、使用场景、现在的做法、困难或风险及支持证据；证据可来自访谈、行为记录、客服问题、业务数据或制度与法规。不要要求所有需求都有同一种量化证据，也不要把“用户想要这个功能”直接改写成“该方案已证明有效”。

区分四种信息：

| 类型 | 写法与处理 |
| --- | --- |
| 用户原话 | 标出谁在什么材料或消息中表达，保留原意 |
| 已核实事实 | 说明数据、文件或工具依据及适用范围；历史材料不当作当前事实 |
| 待验证假设 | 说明推断、影响和验证方式，不伪造依据 |
| 已确认决策 | 记录谁决定了什么、适用范围与必要取舍；建议和沉默不是确认 |

真实性、是否值得现在做、信息是否可实施是不同问题。证据不足时给出当前证据强度与验证办法；用户仍可授权原型或试验，但不能把试验输出宣称为已经验证的产品价值。

## 按影响选择信息要素

| 要素 | 需要明确的信息 |
| --- | --- |
| 问题与来源 | 当前做法、困难或风险、影响、诉求与证据来源 |
| 用户与场景 | 用户角色、环境、触发时机、前置条件 |
| 目标与成功指标 | 期望改善的结果；适用时明确指标定义、基线、目标、周期和数据来源 |
| 范围与优先级 | 本次包含与排除项、必要能力与延期项，以及排序原因 |
| 用户流程 | 从触发到完成的步骤；相关取消、失败、重试和恢复分支 |
| 业务规则 | 条件、状态变化、边界值、限制、计算与例外；冲突如何处理 |
| 数据与权限 | 字段含义、来源、归属、生命周期；角色的查看和操作权限 |
| 交互与体验 | 内容、操作反馈、加载、空状态、错误、成功；必要原型及说明 |
| 质量要求 | 改动涉及的性能、安全、可靠性、兼容性、可访问性或合规要求 |
| 验收条件 | 对应功能在指定前提、操作与环境下应产生的结果及验证证据 |
| 约束、依赖与未知 | 时间、资源、外部系统、风险、假设、待决项与处理责任 |
| 责任与变更 | 谁决定和验收、已确认取舍、版本和变更对流程、任务与验收的影响 |

这是分析维度，不是每次必须展示的十二个空栏目。涉及上线与存量用户时再补迁移、发布、回退、通知与效果观察；不相关的内容省略或简述原因。小文案调整不要求编造业务指标，大范围或高风险功能不能只写主流程。

## 功能要求与两类判据

功能要求描述可观察行为，避免只写“支持管理”“体验友好”“安全可靠”。可用自然语言条件句：当某角色在某前提下执行某操作，系统产生某结果；只在能减少歧义时使用 EARS 等格式，不为格式改写全部对话。

每项重要功能至少有可验证后果，可用“给定……，当……，则……”写 AC。按实际风险覆盖主流程和重要反例，包括无权限、空数据、重复操作、失败或边界情况。为质量要求补足适用环境、负载、可观察阈值或验证方式；阈值未知时标为待定，不自行填入漂亮数字。

- **功能验收**证明表现符合约定：选择三条记录后，结果包含且仅包含这三条。
- **业务成功**证明问题得到改善：完成同一工作所需时间相对实测基线下降，说明目标、样本、观察周期和数据来源。若目标尚未确定，标“待确定”，不能宣称已达成。

业务指标必要时同时考虑副作用，例如提高导入速度是否增加错误任务。功能通过、部署成功或任务标记完成均不能单独证明业务成功。

## 实施准备检查

用证据回答以下问题，不给缺乏依据的百分比分数：

1. 各方能否对用户问题、目标和本次范围形成一致理解？
2. 主要用户流程、规则及重要异常能否确定系统行为？
3. 重要要求是否能由结果、状态或可靠证据判断通过与失败？
4. 文字、原型、术语、权限、规则与验收是否冲突？
5. 已知约束和依赖是否支持该范围，必要技术可行性是否核实或安排验证？
6. 会改变本次范围、权限、数据或验收的关键决定是否明确；其余未知是否标记并有处理方式？

可以在正文给出“探索中”“待关键决策”“可实施”的分析结论及依据；它们不是工具支持的 status 枚举，不写成新业务字段。未决项按影响管理，不要求消除全部未知。若只确定独立子范围，可明确限定后继续已授权工作，不把未确定部分一起派发。

建议或假设不能替代核心业务规则。操作对象、权限、计算、匹配或状态规则未定义时，先核对现有资料与行为；仍有不同合理解释且会显著改变结果或验收时，列为关键未决。例如非空标签搜索的精确/包含匹配会返回不同结果，不能只在 note 写一句“假设包含匹配”就把完整搜索派为可实施；可继续独立且已明确的权限过滤与空查询部分。不会改变已约定能力或验收的表现偏好才可用明确标注的建议推进。

## note 的组织建议

根据任务裁剪，优先保留问题与来源、目标用户和场景、目标、本次范围与非目标、功能及业务规则、异常与权限、验收条件、依赖及假设/未决项。复杂需求可用 FR/AC 编号关联任务与判据，责任和取舍随相关段落记录。超出工具 5000 字限制时先消除重复；仍过长则说明限制，只在用户要求或允许的文档工作范围内写补充文件并在正文引用，不静默丢弃关键规则。
