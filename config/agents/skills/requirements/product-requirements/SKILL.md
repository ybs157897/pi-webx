# 产品需求分析与交付准备

把用户诉求转成足以支持下一步的共同理解。分别判断问题是否有证据、信息是否足以实施、功能是否符合约定、业务价值是否被验证；不要用文档完整度替代任何一个判断。

## 按任务读取参考

- 分析、编写或评审需求：读 [需求质量与规格](references/quality-and-specification.md)，按影响选择要素，不机械填满模板。
- 保存、修订、拆分待办或向群聊交接：读 [产物与工具契约](references/artifacts-and-handoff.md)，再调用本会话实际可用工具。
- 仅查询进展、处理完成回报：核对已有需求版本、待办与证据，不重做访谈或生成新需求。

参考文本使用 `skills_read(name="product-requirements", resource="references/quality-and-specification.md")` 等方式读取，resource 相对本 Skill 目录。Skill 是工作方法，不授予新工具、数据范围或实施权限。

## 分析与收敛

1. **核对对象、意图与已有信息。** 识别探索问题、评审已有规格、修改需求或明确要求实施；结合同话题上下文、用户材料和服务端工作台上下文，复用已确认信息与授权。宿主应用身份不等于需求目标。“这个/这里/它”没有唯一指代时立即简洁澄清，不通过列目录、搜盘、读其他会话或数据库猜对象。对象已明确才读取相关材料；若诉求以某个功能开头，先找到它服务的用户任务和现有困难。
2. **建立证据与决策区别。** 用户原话保留来源；事实说明核实方式；推断标为假设；确认的范围和取舍记为决策。未核实的问题、指标和方案效果保持未验证，不因表达肯定就改成事实。
3. **先处理影响最大的缺口。** 判断缺失是否会改变本次范围、业务行为、权限、数据或验收。能从明确关联的资料自行核实的先核实；目录为空、找不到材料或工具被拒后停止扩大检索。工作台需求用 requirements_context 查询，群聊只读当前投递话题。必须由用户决定的简洁提问并说明影响，只暂停依赖项。可选偏好提出建议并标注假设，不把沉默记为确认。继续整理和验证独立部分。
4. **组织可观察行为。** 从用户角色、触发条件、操作、结果和主要失败分支写规格；规则讲清条件与后果。通常把架构、框架和实现步骤留给代码开发；用户指定或合规、平台要求的技术限制作为约束保留。
5. **检查并选择下一步。** 核对目标、范围、流程、规则、原型和验收是否一致。关键决定明确、主要行为可验收且依赖可处理时，推进已获授权的保存或交接；否则明确待决项、影响与下一步。探索性成果仍可有价值，不强称“可实施”。

## 输出与拆分

先给用户最需要的结论：已明确的需求、关键未决项及其影响，或可实施范围与验收。说明规模与风险相称；小改动只需问题、行为变化、边界和验收，大需求再补完整流程和约束。避免重复整份检查清单、空标题和无意义的完美度评分。

需求规格以 `note` 为主，实际候选事项以 `taskDrafts` 为主。可给正文中的功能与验收设置 FR-01、AC-01 等局部编号，并在对应待办标题中简短引用，确保每项工作能找到完成判据；这些是文档编号，不是数据库 ID。不要给 taskDrafts 增加工具不支持的描述、依赖或验收字段，详细内容写回 note。

新证据或用户纠正到来时，更新受影响规则、范围和验收，移除相互冲突的旧表述；说明哪些任务或结论需要重审。草稿保存、待办导入、开发完成、功能验收、业务效果验证和用户正式接受分别汇报。
