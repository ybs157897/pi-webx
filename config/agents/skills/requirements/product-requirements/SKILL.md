# 产品需求分析与交付准备

把用户诉求转成足以支持下一步的共同理解。分别判断问题是否有证据、信息是否足以实施、功能是否符合约定、业务价值是否被验证；不要用文档完整度替代任何一个判断。

## 按任务读取参考

- 分析、编写或评审需求：读 [需求质量与规格](references/quality-and-specification.md)，按影响选择要素并做影响分析，不机械填满模板。
- 保存、修订、成文或向群聊交接：读 [产物与工具契约](references/artifacts-and-handoff.md)，再调用本会话实际可用工具。
- 仅查询进展、处理完成回报：核对已有需求版本、待办与证据，不重做访谈或生成新需求。

参考文本使用 `skills_read(name="product-requirements", resource="references/quality-and-specification.md")` 等方式读取，resource 相对本 Skill 目录。Skill 是工作方法，不授予新工具、数据范围或实施权限。

## 分析与收敛

当前会话绑定的工作空间整体就是当前项目；根目录包含多个模块也不改变项目身份，不要再询问项目名称。项目身份与背景以本会话提供的绑定信息和项目材料为准。需要核实事实时，按本会话实际工具能力读取绑定工作区内直接相关的 README、源码、配置和需求材料，不扩展到工作区之外。服务端需求上下文提供绑定身份与已有需求摘要；摘要不代表用户选择或授权了其中任何需求。

1. **核对对象、意图与已有信息。** 识别探索问题、评审已有规格、修改需求或明确要求实施；结合同话题上下文、用户材料和需求上下文，复用已确认信息与授权。先依据现有信息识别“这个/这里/它”指向的功能或行为；只有仍存在会改变业务范围或验收的不同解释时，才简洁询问具体差异，不询问项目身份。若诉求以某个功能开头，先找到它服务的用户任务和现有困难。
2. **影响分析。** 用只读检索工具（read/ls/grep/find）在绑定项目内定位相关实现：功能入口与路由、调用方与被调用方、数据结构与迁移、相邻交互行为、配置与文档、测试面。每个影响点标注定位依据与处理方式（必改 / 需适配 / 需回归验证）。先核实再断言：检索只用于定位证据，未核实的判断标为假设并进入待对齐清单，不写成事实。
3. **变更判定。** 成文前用 requirements_context 按主题检索历史需求库：对应功能已有记录时判定为变更并标 change——该记录是本会话的未导入草稿才传 id 修订，已导入或非本会话的历史需求不改写，新建记录并在 `## 变更判定` 写明对应 REQ-ID 与受影响的旧验收。确认不是已有功能才按新建处理。判定依据写入文档，category 取 `new | change | fix | enhancement`（默认 new）。
4. **建立证据与决策区别。** 用户原话保留来源；事实说明核实方式；推断标为假设；确认的范围和取舍记为决策。未核实的问题、指标和方案效果保持未验证，不因表达肯定就改成事实。
5. **先处理影响最大的缺口。** 判断缺失是否会改变本次范围、业务行为、权限、数据或验收。能从绑定工作区内直接相关的资料自行核实就先查；找不到材料或工具被拒后不扩大到工作区之外。已有需求记录用 requirements_context 查询，群聊只读当前投递话题。只有仍无法核实且必须由用户决定的关键业务缺口才提问，并说明影响，只暂停依赖项。可选偏好提出建议并标注假设，不把沉默记为确认。继续整理和验证独立部分。
6. **组织待对齐清单。** 把影响点与实施细节整理成 Q1、Q2… 编号清单，每条一句「问题 + 影响哪个决定」，请用户逐条回应后再成文。影响点必须主动列出，不能自作主张吞掉；但只列会改变范围、行为、数据、依赖或验收的项，其余按小需求裁剪，不退回避重盘问模板。
7. **组织可观察行为。** 从用户角色、触发条件、操作、结果和主要失败分支写规格；规则讲清条件与后果。通常把架构、框架和实现步骤留给代码开发；用户指定或合规、平台要求的技术限制作为约束保留。
8. **检查并选择下一步。** 核对目标、范围、流程、规则、原型和验收是否一致。待对齐清单已得到回应、主要行为可验收且依赖可处理时，推进已获授权的保存或交接；否则明确待决项、影响与下一步。探索性成果仍可有价值，不强称“可实施”。

## 输出与成文

先给用户最需要的结论：已明确的细化结果、编号待对齐清单及其影响，或可实施范围与验收。说明规模与风险相称；小改动只需问题、行为变化、边界和验收，大需求再补完整流程和约束。避免重复整份检查清单、空标题和无意义的完美度评分。

note 按固定章节成文：`## 目标`、`## 详细内容`、`## 范围影响`（受影响功能点与对策，逐点写明定位依据与处理方式）、`## 验收标准`；category 为 change 时补 `## 变更判定`（对应哪条历史需求、为何算变更、受影响的旧验收）。可给正文中的功能与验收设置 FR-01、AC-01 等局部编号，这些是文档编号，不是数据库 ID；实施拆解写在 note，不外溢成多条待办。

taskDrafts 默认恰好 1 条，标题表达这个需求的整体交付，可引用需求标题；仅当用户明确要求分批排期时才拆多条。不要给 taskDrafts 增加工具不支持的描述、依赖或验收字段，详细内容写回 note。

新证据或用户纠正到来时，更新受影响规则、范围和验收，移除相互冲突的旧表述；说明哪些任务或结论需要重审。草稿保存、待办导入、开发完成、功能验收、业务效果验证和用户正式接受分别汇报。
